# R2 — Security review of the internet-reachable surface

What an attacker can reach through `tempcode.landonhale.com` (the box's
fixed-port listener on `127.0.0.1:7677` behind the Cloudflare tunnel) and
`hub.landonhale.com` (the Cloudflare Worker), reviewed 2026-10-20 against
`master`. Read-only on the repo; nothing was changed but this file.

Cloudflare Access (the three user emails) fronts `/ui` and the Coolify
dashboard only. `/healthz`, `/api/*`, `/pair`, `/ws`, `/mcp` and `/asset/*`
reach the listener with no Access gate and carry their own bearer/cookie
auth — so every finding below is about those bearer surfaces, which an
attacker reaches directly.

Proof harness: an isolated `startServer` on a throwaway database, aliax
vault and ephemeral fixed port (the shape of `scripts/e2e-remote.ts`), plus
two direct-import unit checks. Scripts lived under `/tmp`, never the box's
live service or the installed app. `ssh box` was read-only. No key, code,
ticket or secret is reproduced here.

## Severity at a glance

| # | Severity | Surface | One line |
|---|---|---|---|
| H1 | HIGH | contract `fs.*` / `search.project` / `git.*` | A client **read** key reads any file the host process can read, anywhere on disk. |
| H2 | HIGH | contract `fs.*` / `git.clone` | A client **operate** key writes, deletes and clones to any path on disk. |
| M1 | MEDIUM | pairing | One pairing code redeemed concurrently mints several keys (single-use is not atomic). |
| M2 | MEDIUM | account sync | A connected peer can inject a new access-only account entry the host never paired. |
| M3 | MEDIUM | webhooks / hub | Webhook and subscription URLs are not blocked from private ranges or cloud metadata (admin-gated SSRF). |
| L1 | LOW | pairing links | A loopback caller with a spoofed `Host` can poison the learned pairing-link origin. |
| L2 | LOW | `/api/hello` | Unauthenticated hello discloses the hostname and app version. |
| L3 | LOW | `/pair` | The pair page allows inline script in its own CSP. |

## The capability gate (contract over `/ws`) — mostly sound, two gaps

The gate itself is correct: `attach()` resolves `requiredCapability(req)`
before any handler, rejects `local` methods for every remote principal, and
honours the `session.create permission:'auto'` → `approve` param rule
(`src/main/server/index.ts:540`, `src/shared/capabilities.ts:239`). The
single-tenant model (every client key sees every project and session) is by
design. The problem is not the gate — it is that a family of host-wide file
methods is mapped to `read`/`operate` instead of `local`.

| # | Severity | file:line | Attack (one sentence) | Fix |
|---|---|---|---|---|
| H1 | HIGH | `src/shared/capabilities.ts:60-71,77,106` ; handlers `src/main/server/fsgit.ts:13-26,48`, `src/main/server/fspaths.ts:512,524,451,496,251` | A `client` key with only **read** calls `fs.readText` / `fs.readBase64` / `fs.readPreview` / `fs.listPath` / `fs.inspectPaths` / `fs.statFiles` / `search.project` / `git.log` on any absolute path or cwd — these resolve with `expandHome`+`resolve` and are **not** fenced to any workspace, so the whole filesystem the process can read is exposed (on the box, under `agents`: every repo, the thread SQLite DB, `~/.config/gh/hosts.yml`, the CLI credential files, `environment.json`). | Mark the whole-host donor `fs.*`, `search.project` and cwd-taking `git.*` methods `local`, or fence them to the open project/workspace roots for a remote principal (reuse the realpath fence in `media.ts`). `file.read`/`fs.read` are already fenced — extend that to the donor family. |
| H2 | HIGH | `src/shared/capabilities.ts:133-140` ; handlers `src/main/server/fsgit.ts:15-19,26,34`, `src/main/server/fspaths.ts:542,292,346,407,431` | A `client` key with **operate** calls `fs.writeText` / `fs.createPath` / `fs.deletePath` / `fs.copyPath` / `fs.movePath` / `fs.renamePath` on any path, and `git.clone` to pull an arbitrary URL into any parent directory — none are workspace-fenced, so it is arbitrary host write/delete and a clone-anywhere primitive. | Same fence as H1 for the write methods; confine `git.clone`'s `parent` to the open roots. |
| — | OK | `src/main/server/index.ts:158-170` | `file.read` and `fs.read`/`fs.write` (project `jail()`) refuse paths outside app-managed roots — verified refused in the harness. | — |
| — | OK | `src/main/server/remote/facade.ts:720-752,956-960` | The `/mcp` bot surface never exposes `fs.*`/`git.*`; the `mcp` audience is capped at read+operate (`auth.ts:52`), `start_session permission:'auto'` is downgraded without `approve`, and `respond` refuses a permission prompt without `approve`. The H1/H2 reach is the `client` audience on `/ws`, not `/mcp`. | — |

Proved (isolated instance): a read-only key returned the contents of a file
placed outside every project and workspace root via `fs.readText`,
`fs.readBase64`, `fs.readPreview`; listed a directory outside every root via
`fs.listPath`; ran `git.log` in an unrelated repo; and grepped an arbitrary
directory via `search.project`. An operate key wrote, created and deleted a
path outside every root. Controls confirmed the gate otherwise holds:
`fs.writeText` was refused for the read key, `file.read` was refused as
outside app-managed directories, and `session.permission` was refused
without `approve`.

## Pairing, tickets, cookie, header trust

| # | Severity | file:line | Attack (one sentence) | Fix |
|---|---|---|---|---|
| M1 | MEDIUM | `src/main/server/remote/auth.ts:425-451` | `exchange()` reads the open pairing, then awaits `createKey` (scrypt) before the `UPDATE … WHERE consumed_at IS NULL`, so N concurrent redeems of one code all pass the open-check and all mint keys — "single use" is not atomic. | Consume the code in one conditional `UPDATE` and act only when `changes === 1`, before minting; or wrap read-consume-create in a transaction / in-process lock keyed by the code. |
| L1 | LOW | `src/main/server/remote/listener.ts:94-109,165-169` ; `handlers.ts:57-59` | A caller on loopback that sets `Host: evil.example` + `X-Forwarded-Proto: https` gets `learnedOrigin` written, and the next pairing link becomes `https://evil.example/pair#<code>`; a victim pairing through that link sends the code to the attacker. | Learn the origin only from an allowlist of expected hostnames, or drop learned-origin now that `publicOrigin` is set and takes precedence. |
| L2 | LOW | `src/main/server/remote/listener.ts:203-217` | `GET /api/hello` with no credential returns `name: hostname()` and the app version to any internet caller. | Omit `name`/`version` from the unauthenticated hello, or gate them behind a valid key. |
| L3 | LOW | `src/main/server/remote/ui.ts:95` | The `/pair` page ships `script-src 'unsafe-inline'`; it is a static first-party page that echoes nothing server-side, so there is no injection point today, but the allowance is broader than needed. | Move the pair script to a hashed/`'self'` file so the page needs no `unsafe-inline`. |
| — | OK | `auth.ts:380-405,480-487` | Tickets are 30 s, single-use (deleted on consume), bound to the key id, re-checked against revocation, and never logged; a reused ticket is refused (proved in `e2e-remote`). | — |
| — | OK | `listener.ts:112-116,177-181,344-349` | The session cookie is `HttpOnly; SameSite=Lax; Secure` (when the proxy says https); cookie-borne non-GET requests and the `/ws` upgrade enforce an `Origin` match. | — |
| — | OK | `ui.ts:60-71` | The `/ui` CSP rewrite only appends the host to `connect-src` and adds `'self'` to `frame-src`; it never touches `script-src`. | — |
| — | OK | `listener.ts:96-100,407` | `cf-connecting-ip`/`x-forwarded-proto` are trusted only when `req.socket.remoteAddress` is loopback, and the listener is hardcoded to `127.0.0.1`, so it cannot be bound off-loopback from settings (only the port is configurable). | — |

Proved: three concurrent redeems of one fresh pairing code all answered 200
and the key table grew by three; a later redeem of the same code was
refused. The spoofed-`Host` loopback request caused the next admin-created
pairing link to point at `https://evil.example/pair#…`.

## Account sync and peer links

| # | Severity | file:line | Attack (one sentence) | Fix |
|---|---|---|---|---|
| M2 | MEDIUM | `src/main/server/remote/accountSync.ts:274-281` ; `aliax-core/src/sync.ts:233-236` | A peer on an established link (the box, toward the Mac that holds its admin key) can send an unsolicited `account` push for a profile the receiver has never seen; `applyTransfer` lands it as a **new** access-only entry whose `owner` is taken from the attacker-chosen `profile.owner`, so a compromised peer can inject account rows the host never paired. | In `onPeerPush`, require `push.transfer.profile.owner === from` and that a matching profile already exists (match on accountId/email) before `applyTransfer`; reject a transfer that would create a brand-new profile over a push. |
| — | OK | `aliax-core/src/sync.ts:153-170,198-237` ; `refresh.ts:84-85,124` | A refresh token is sent only by the owner and only in a `handoff` that names the recipient as the new owner; `stripRefresh` removes it from every access copy; `refreshClaude`/`refreshCodex` never call the token endpoint for a profile owned elsewhere (they `askOwner` instead). |
| — | OK | `src/shared/capabilities.ts:226-227` ; `index.ts:540-544,550-556` | `accounts.push`/`accounts.pull` are `admin`; a non-admin remote caller is rejected by the gate before the handler. `accounts.sync`/`accounts.setHome` are `local`. |
| — | OK | `src/main/server/remote/peers.ts:91-99` | A peer's hello is checked against the saved environment id; a host answering as a different id is closed and not trusted. |
| — | OK | `aliax-core/src/sync.ts:226-235` | `applyTransfer` refuses a handoff not addressed to this host and an access copy where this host already owns the grant, and never saves an older access token — so a peer cannot overwrite an owned credential. |

M2 is reported from the code path; end-to-end exploitation (the injected
access-only entry being chosen by the gateway for a real request) was **not
verified**, and on the box the trusted peer is the Mac. The fix is cheap
regardless.

## Webhooks and the notifier

| # | Severity | file:line | Attack (one sentence) | Fix |
|---|---|---|---|---|
| M3 | MEDIUM | `src/main/server/remote/webhooks.ts:50-62` ; `infra/hub/src/validation.ts:23-34` | The webhook URL check requires https and no credentials but does **not** block private ranges, loopback-by-IP (hub) or cloud-metadata hosts, so a holder of an admin key (app) or the hub admin key can aim signed POSTs at `169.254.169.254`, `10.0.0.0/8`, `metadata.google.internal`, etc. — server-side request forgery from the box or the Worker. | Reject private, loopback, link-local and ULA address literals and known metadata hostnames; resolve the host and re-check before connect to blunt DNS rebinding. |

## Not verified

- **M2 routing impact** — that an injected access-only account is actually
  selected by the gateway for a live request. The injection path is proved
  from code; the downstream effect is not.
- **L1 in production** — the learned-origin poison needs a loopback caller
  with a chosen `Host`. Cloudflare routes the tunnel only for its configured
  hostnames, and `remote.publicOrigin` is set (and beats `learnedOrigin`),
  so a pure internet attacker could not reach it in the current topology;
  only the mechanism is proved.
- **M3 live SSRF** — the validators were shown to accept internal URLs; no
  POST was fired at a real internal address from the box or the Worker.

## Fixed (thread F1, 2026-10-20, on master)

Every finding but M2 is closed by the commits below; M2 (account sync peer
injection) is thread F2's. Proof: `bun run script:e2e-remote-fence` (now in
the release gate) plus a unit case per finding in the matching test file;
`bun scripts/e2e-remote-ui.ts` and `bun run ios:test:client` still pass, so
the web and phone clients kept working.
