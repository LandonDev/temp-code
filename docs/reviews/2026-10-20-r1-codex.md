**V — account sync and token ownership**

Reviewed dd734b4 and a12368a (v248–v249), plus aliax-core 9806651. The capability gate in src/main/server/index.ts:540 precedes accounts.pull and handleM3a/accounts.push; both require admin. Ordinary pull and broadcast use exportAccount(access), remove Claude appSession and strip the service refresh field; receiving an access copy strips it again before the encrypted vault write. Handoff exports a full grant, installs it on the named owner, then confirms and strips the sender. takeOver uses releaseTo before replying. Owner guards protect ordinary Claude/Codex refresh calls; the findings below concern transitions those guards do not cover. Activation can also write the stored blob to the local CLI credential store. No explicit token logging appeared in the normal sync/refresh paths inspected. Not verified: real setup-token failure output, real provider rotation, and nested Cursor credential fields captured from an actual IDE. No real credential store was read.

## F2 closure (2026-10-20 UTC): V, account sync and token ownership

Thread F2 took the five V findings above and R2's M2 (a peer planting an
account over an `account` push). The invariant behind all of them: exactly
one host ever refreshes an account's grant, no step leaves zero or two
refreshers, and a host accepts account state only for accounts it paired
or owns. aliax-core `be4d1ab` (pinned by temp-code `b3bb3be`) carries the
core; temp-code `b3bb3be` carries the host side, the tests and the proof.

| Finding | Commit | Fix |
| --- | --- | --- |
| HIGH `aliax-core/src/refresh.ts:103` | aliax-core `be4d1ab` | `src/lock.ts`: one asynchronous lock per stored profile. `once()` runs every refresh under it and `beginHandoff` holds it from the export to commit or abort, so a refresh that began before a handoff finishes first (the handoff carries the rotated token) and none starts during one. The save after the token endpoint answers (`saveRefreshed`) re-reads the profile and never writes a refresh token into a vault this host no longer refreshes for: the caller gets the fresh access token once, stripped. |
| HIGH `aliax-core/src/sync.ts:221` | aliax-core `be4d1ab`, temp-code `b3bb3be` | The receiver saves before it answers, and says what it saved: `applyTransfer` lands a handoff provisionally (the row keeps naming the sender, so nothing there refreshes it yet) and answers `refreshFingerprint` (a digest of the refresh token on file, never the token); an older handoff onto a host with no refresh token is refused as `stale`. The sender (`pushOne`) strips only on an ok whose fingerprint equals the one it sent, then `accounts.released` makes the receiver the owner (`claimHandoff`); an unheard release is told again on every sync while `releasedAt` stands. |
| HIGH `src/main/server/remote/accountSync.ts:236` | aliax-core `be4d1ab`, temp-code `b3bb3be` | The Codex adapter gets `liveFingerprint`/`fingerprintOf` on sha256 of the refresh token in `auth.json` (`$CODEX_HOME`, else `~/.codex`), the same token-level check claude.ts has, so the grant the CLI on this machine is signed in with is never handed off; `liveLineage` also refuses when an adapter cannot fingerprint grants (Cursor). The e2e proves the access-copy-only push and the handoff once the CLI has rotated onto another token. |
| MEDIUM `aliax-core/src/sync.ts:249` | aliax-core `be4d1ab`, temp-code `b3bb3be` | `releaseTo` is gone. A `takeOver` pull hands the grant out under the lock and keeps it pending (`RELEASE_TIMEOUT_MS`, 30 s): the owner strips only on the taker's `accounts.confirm` carrying the fingerprint, else keeps refreshing; a late or wrong confirm is refused. | MEDIUM `src/main/server/remote/peers.ts:231` | temp-code `b3bb3be` | `PeerLink.credential` is a digest of the saved key (`peers.ts keyFingerprint`); `Peers.refresh` rebuilds a link whose key changed even when its routes did not, so sync returns after a re-pair following a revoked key (4001). |
